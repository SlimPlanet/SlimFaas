Application, Resource and Autoscaling Benchmarks

SlimFaas includes a reproducible native-local benchmark for the warm synchronous proxy path, asynchronous enqueue and delivery, and scale-to-zero followed by PromQL scale-out.

CPU, RAM and throughput

The application benchmarks already export these measurements. Unit tests check the collectors and report calculations with fixtures; their execution times are not performance results. Use the following fields for the website results table:

Workload Throughput CPU RAM Evidence

HTTP async, paced and burst Accepted messages/s (HTTP 202), excluding delivery drain Aggregate runtime CPU ms/accepted message, including delivery drain Sampled peak aggregate working set, MiB, including drain LatencyRuns[].AsyncResources; AsyncWorkloads[].Resources and .RatePerSecond

The HTTP summary.md contains a combined throughput/CPU/RAM table with repetition counts, request failures, missing deliveries and duplicates. CPU is CPU time per accepted message or successful request, not CPU utilization %. RAM is measured in MiB (bytes / 1,048,576). The runtime totals exclude the load generator, function processes, local supervisor and container/VM overhead; background consensus and diagnostics work remain included. A 500 ms HTTP or approximately 1 s platform sampling interval can miss shorter RAM spikes. Acceptance throughput must not be relabelled as delivery throughput. Keep delivery counts, latencies and drain results beside it.

Complete feature campaign and offline export

The default .bin/run-platform-matrix.py blocks now include data and features, in addition to the existing HTTP and MemoryLab set/mixed controls. The same frozen C# driver generates work in every ABBA role. Python controls platforms and receiver processes; it does not generate the timed feature load. Build the drivers and both reference/candidate products before measurements. Container images must contain the same updated benchmark tools, official SDKs and fixture sources; an old image with a new launcher is not a compatible driver.

Block Cases Integrity and timing
http Direct/sync/async; steady, paced, burst; existing payload/concurrency matrix IDs, delivery, duplicates, queue drain; acceptance and completion windows are separate
data slimdata-set, get, set, delete, hashset, hashget, hashdelete, increment, decrement Isolated operations; reads/deletes preseed outside load; final values checked on every node. Set reads use the consistent API; hashset reads retain their documented visibility semantics
data files-upload, files-download, files, files-unique Upload only, preseeded download only, cross-node upload/read cycle, bounded unique uploads. Changing overwrite contents, length and SHA-256 verification, all-node final validation
features Streams with one/two functions 200 accepted messages, independent per-function receipts, missing/duplicate/corrupt checks and committed ACK/lag drain
features Jobs 200 real jobs, independent started/completed receipts and Succeeded state on every node; request latency and submission-to-start samples
features .NET and Python WebSocket sync, async, events Official SDK receivers; full response SHA-256, first-byte timing, callback receipts and two-function event fan-out

New cases use concurrency 1/4/16 and three repetitions by default. Files and WebSocket use the HTTP payload list. Isolated data cases have an unmeasured warmup. Reads are preseeded and verified before collection. Delete cases stop when each seeded key has been deleted once; unique file uploads are bounded to 200 operations. After successful all-node validation, the data block deletes only its own file IDs through the public API, outside measurement. Failed data, WALs, journals and raw results remain available. Direct MemoryLab invocations retain files unless --cleanup-owned-files true is supplied. Files report logical payload MiB/s, not the sum of upload and download network traffic. Runtime RSS excludes the generator's payload buffers. In the direct HTTP control, runtime CPU/RAM represent idle cluster background work, not the target function. Mixed workload CPU/RAM describe the whole mix, never each constituent operation. Jobs keep a configured dispatch limit of 16 in this feature profile; request concurrency and job dispatch parallelism are different settings.

Receiver receipt polling and queue/job state confirmation are included in the observed completion window, so completion rates are conservative and distinct from acceptance rates. DrainSeconds records the additional observation time. For WebSocket async workloads, successful receiver receipts and refreshed all-node queue totals verify drain on the isolated benchmark cluster. Virtual functions do not publish the per-function depth gauges used by the HTTP benchmark. The Jobs profile launches real processes/pods; it measures their lifecycle, including startup. It does not claim isolated scheduler capacity. Keep cold start, timeout, cancellation, retries, reconnect and recovery tests in the existing reliability campaigns rather than mixing faults into healthy capacity.

The shared benchmarks/Common/ClusterResourceMonitor.cs collector takes explicit initial/final samples and periodic 500 ms samples. Every node must have live CPU, RSS and an unchanged process start identity. Counter resets, missing nodes and invalid samples cannot become zero usage. Async Raft diagnostics additionally wait for a refresh on every node; the final refresh wait is outside the live CPU window. MemoryLab's older memory.csv remains available for historical adapters.

There is no overall campaign duration limit. The full feature matrix can take more than one night; use --blocks data or --blocks features for separate, fresh campaigns. Individual requests/drains remain bounded. Kubernetes phases have a configurable phase_timeout_seconds (default seven days). Disk guards stop new cases below 20 GiB free. Completed attempts and failures are retained. For capacity measurements on a space-constrained host, set workload_args to include --no-http-journal or --no-data-journal. These options retain compressed HTTP latency samples or data operation samples, resource data and integrity checks. Use the detailed journals for transport reconciliation. Keep the same journal setting in each comparison role. Use --file-work-budget-mib to cap the logical payload in each warmup and measured file case. Its value must fit one payload per worker. A capped test may complete before its duration limit. Use --feature-scenarios jobs ws or --data-scenarios files files-download to run selected cases in a fresh output directory. A partially executed phase without execution.json is deliberately not restarted in place: inspect and stop its owned processes, retain its directory, then use a fresh campaign. Never attach to an unverified saved PID or change a WAL marker.

campaign-identity.json freezes configuration, selected blocks, launcher hashes and local executable/managed dependency hashes. Resume refuses changes or a legacy campaign without this identity. Immutable image digests are required for container configurations. Comparisons also verify matching driver assemblies and fixture hashes before accepting evidence. The same output directory cannot be used for a new candidate. A known candidate integrity failure remains FAIL even if its reference has missing measurements or a later repeat passes. Incomplete measurements remain INCONCLUSIVE. New feature performance is OBSERVED, not a non-regression PASS: retain the established HTTP/MemoryLab budgets and calibrate new budgets before asserting optimization gains.

Offload, WAL and queue optimization candidates

Use 1 MiB (1,048,576 bytes) as the general async body offload threshold. Bodies larger than the threshold use Files. WAL directories created by SlimData on Windows use 64 KiB. New Linux and macOS WALs use the host page size. Preserve the stored geometry when reopening an existing WAL.

In the independent macOS repeat, a 512 KiB threshold increased completed throughput for 1 MiB bodies at concurrency 16 from about 12 to 190–199 messages/s. CPU fell from 124–127 to 22–23 ms per accepted message, and sampled peak RAM fell from 1,596–1,643 to 562–618 MiB. The overall threshold comparison exceeded the guardrails in all eight reference–candidate pairs, including async bursts. The comparison of fresh 64 KiB WALs with the 16 KiB macOS default also exceeded at least one guardrail in every pair of both campaigns. Keep the defaults above. See the initial campaign and repeat for the full case tables and interrupted attempts.

In both campaigns, Jobs, Streams and WebSocket recorded all 16,000 expected receipts and no missing, duplicate or corrupt receipts. The code comparison exceeded HTTP non-regression guardrails. MemoryLab passed Set and mixed at concurrency 48 in both campaigns. At concurrency 12, the Set throughput failure recurred and the mixed workload passed only in the repeat.

Run the benchmark

One managed driver, benchmarks/SlimFaas.Benchmarks, provides micro, target, run, compare and the offline report command:

dotnet build benchmarks/SlimFaas.Benchmarks -c Release \
  -p:PublishAot=false -p:SelfContained=false -p:SkipClientAppBuild=true
dotnet benchmarks/SlimFaas.Benchmarks/bin/Release/net11.0/SlimFaas.Benchmarks.dll micro --list flat
dotnet benchmarks/SlimFaas.Benchmarks/bin/Release/net11.0/SlimFaas.Benchmarks.dll micro --extended --filter '*RoutingQuery*'
dotnet benchmarks/SlimFaas.Benchmarks/bin/Release/net11.0/SlimFaas.Benchmarks.dll target --port 31080
# With the runtime, target and scaling fixture already running:
dotnet benchmarks/SlimFaas.Benchmarks/bin/Release/net11.0/SlimFaas.Benchmarks.dll run --profile async-queue
dotnet benchmarks/SlimFaas.Benchmarks/bin/Release/net11.0/SlimFaas.Benchmarks.dll compare \
  --criteria non-regression --baseline before/results.json --candidate after/results.json

micro retains BenchmarkDotNet filters, exporters and --extended. Existing option-only microbenchmark invocations remain accepted. Invoking without a command returns exit code 2; help returns 0; malformed commands return 1. compare retains exit codes 0 (pass), 1 (failure) and 2 (inconclusive). The HTTP driver retains its exports, load profiles and deadlines. The scripts build this driver before measurement. Use the same frozen driver and configuration for both sides of each new application comparison. Record the driver hash separately from each runtime hash. Earlier source-pinned reports retain their original project names and binaries.

The driver runs managed code even when its targets are Native AOT executables or containerized runtimes. Build and publish the measured products separately with their own settings; the managed driver does not change their compilation mode. For a framework-dependent driver publication, use the same global PublishAot=false, SelfContained=false and SkipClientAppBuild=true properties. The platform tools image publishes a self-contained, untrimmed managed driver.

Analysis scope and ownership

The C# drivers own workload generation, application timing, exports and comparison criteria. Python coordinates environments/faults and independently reconciles receipts; shell scripts provide launch/environment adapters. Shared paths should delegate to those owners instead of introducing a second load or statistics loop.

Benchmark C# projects are excluded from Sonar with SonarQubeExclude, while the targeted script inventory supplies sonar.exclusions. Runtime, SDK, release and production tools stay eligible for analysis. Benchmark builds/tests continue in CI. Coverage exclusions alone do not exclude static analysis. The completed-scan check waits for processing, checks submitted C# project classification, rejects indexed benchmark sources, and verifies production coverage import. PR APIs can omit unchanged files, so their absence is checked against submitted project metadata rather than treated as an analysis exclusion. See the scope investigation.

The quick profile is intended for a smoke test and takes a few minutes:

BENCHMARK_PROFILE=quick .bin/slimfaas-local-benchmark.sh

On Windows, run the script in Git Bash with Python 3.10+. The launcher places the runtime and its descendants in an owned Windows Job Object before execution. Normal completion and an abrupt launcher exit both close the entire process tree. Occupied benchmark ports are rejected before starting or cleaning state. Run python .bin/test-local-benchmark-host.py to verify those lifecycle checks.

Fresh Windows WALs use recorded 64 KiB data chunks; existing unmarked volumes keep their original geometry. Preserve wal/slimdata-chunk-size with the WAL. The Windows investigation retains the failed controls, reproduction commands and validation of large messages, Streams and recovery. This changes neither the load nor its request deadlines.

Compare an optimization with its baseline

For release safety checks, add --criteria non-regression to the comparison command below. The default remains optimization. Non-regression evaluates the complete sync, async, paced/burst and scaling evidence without requiring the 20–50% optimization targets. It retains the existing 10% throughput/tail guardrails, 20% CPU/message, 10% RSS and 2x Raft-entries/message limits. A missing measurement or failed reference produces INCONCLUSIVE (exit 2), never a passing result.

Async resource collection waits for a fresh diagnostics sample on every node before sending measured requests. CPU and RSS come from the live process collectors across load and delivery drain. After drain, the collector waits for each node's five-second diagnostics exporter to refresh before reading the final Raft counter. This wait is outside the timed load and the CPU/RSS window; the Raft delta includes background entries within that exporter window. It does not extend the 180-second delivery deadline. Initial, final process and final diagnostics snapshots, including per-node timestamps and counters, are retained in AsyncResources / focused-workload Resources for audit. A missing counter, counter reset or refresh timeout cannot produce passing resource evidence. Process start time and CPU/diagnostics/Raft counters are checked per node at each sample and boundary: progress on another node cannot mask a reset. The focused paced/burst comparisons apply the same +20% CPU/message, +10% RAM and 2x Raft/message limits to the median resources of each shape; their resource deltas are retained in comparison.json and comparison.md.

Earlier subsecond bursts could finish between periodic samples and report zero CPU or Raft work. Keep those observations as INCONCLUSIVE and rerun both revisions with the same corrected driver; do not backfill their missing samples.

Verify kind's rootless prerequisites, including cgroup v2 delegation. The kind nodes need a VM-native /evidence mount from /var/home/core/slimfaas-pr506. The launcher creates dedicated labelled namespaces, retained persistent volumes, three anti-affined StatefulSet nodes, actual function Deployments and Jobs. Generators and functions run inside the cluster through Services and pod DNS. Port-forwarding is unnecessary for measurements. Campaign namespaces must fit Kubernetes' 63-character limit, including the matrix block, attempt and ordinal suffixes. PersistentVolume names append a storage suffix and can exceed the label-value limit, so volumes carry the campaign ownership label without an app label. Their unique names, claim references and retained storage paths identify each node's data. A launch with unbound claims has no valid workload measurement; preserve its API errors and replay after correcting the deployment with fresh campaign identities. Each matrix phase keeps launcher manifests, ownership records and Kubernetes diagnostics under controller/, alongside its workload reports. The launcher requires this controller directory to be new; existing phase metadata must not be used as the controller output or overwritten during a resume.

Before exporting a Kubernetes phase, stop scales only Deployments and StatefulSets carrying that campaign's label. What is measured

Warm synchronous overhead

The benchmark target is one minimal HTTP/1.1 server. The driver calls that exact process in two ways:

  1. directly at http://127.0.0.1:31080/echo;
  2. through /function/benchmark-latency/echo.

For each payload size and concurrency, the report includes throughput and HTTP p50, p95, p99, and maximum latency. It then subtracts the direct percentile from the SlimFaas percentile in milliseconds and percent. Calling the same process on both paths isolates the warm routing/proxy overhead from application work.

The standard matrix uses:

  • payloads: 64 B, 4 KiB, 256 KiB, and 2 MiB;
  • closed-loop concurrency: 1 and 16;
  • warm-up: 2 seconds;
  • measurement: 10 seconds;
  • repetitions: 3.

The report uses the median percentile across repetitions and the mean throughput. The driver alternates direct/proxy order between cases to reduce systematic CPU frequency and temperature bias.

Asynchronous latency

Each async case reports two different clocks:

  • acceptance latency: client send until SlimFaas returns HTTP 202 after the request has been durably enqueued;
  • arrival latency: client send until the target handler starts, including enqueue, queue wait, dispatch, and request-body transfer.

For both clocks, the report gives the mean (the simple average) and p50/p95/p99. For example, p95 means that 95% of messages were no slower than that value. The mean is the easiest headline number, while p95 and p99 reveal occasional slow messages that an average can hide. The target also records completion latency in results.json. The target and driver are local processes on the same clock, so UTC ticks can be compared without a network clock-synchronization error. The benchmark waits for every accepted message to be observed by the target and for queue metrics to remain at zero before starting another case.

The 2 MiB case is intentionally above SlimFaas' default 1 MiB async body-offload threshold (strictly greater; exactly 1 MiB stays inline). This makes the matrix cover both inline queue payloads and the cluster-file path. Record SlimFaas__AsyncBodyOffloadThresholdBytes when overriding that default; vary it separately from the fresh WAL geometry and keep it identical across comparison brackets. See async body configuration.

The async profile also records throughput, missing and duplicate IDs, errors, expirations, Raft entries per accepted message, process CPU per message, and peak aggregate SlimFaas working set. The paced scenario measures how quickly a nearly idle queue wakes without waiting for the polling fallback. The burst scenario measures coalescing and backpressure under sudden load.

Scaling speed

benchmark-scale starts at zero replicas. The driver sends a burst of 200 async messages at concurrency 32; each target request takes 250 ms and each replica is limited to one concurrent request. The following durations are measured from the first client send:

  • first and last HTTP 202;
  • desired replicas changing from 0 to at least 1;
  • first ready replica;
  • desired replicas reaching 4;
  • all 4 replicas becoming ready;
  • the ready, in-flight, and retry queues returning to zero.

The first delivered /work request makes the benchmark target expose slimfaas_benchmark_scale_pressure 4 for 30 seconds. SlimFaas scrapes it every second and evaluates max_over_time(slimfaas_benchmark_scale_pressure[30s]). This deterministic demand signal exercises metric discovery, scraping, the internal metric store, PromQL evaluation, scale policy application, local process launch, and health readiness. Queue metrics are observed independently to measure backlog and drain time.

Interpret the result correctly

  • Subtract percentiles in milliseconds first. A sub-millisecond direct baseline can make a small absolute delta look large as a percentage.
  • Async HTTP 202 is enqueue latency, not execution latency. Use target delivery percentiles for end-to-end dispatch behavior.
  • Native local scaling measures SlimFaas plus operating-system process startup. It deliberately excludes Kubernetes scheduling, admission, image pulls, CNI, and container runtime time. Run the same driver against a Kubernetes deployment when those costs are part of the question.
  • Function status endpoints have short caches. Scaling times are externally observed milestones with that polling resolution, not internal timestamps.
  • Avoid unrelated workloads, power-saving mode, thermal throttling, and debug builds. Keep the same host, SDK, commit, and matrix for before/after comparisons.
  • A single run is exploratory. Use the standard repetitions, compare medians, and retain the raw manifest and samples for a publishable result.

See Native Local Development Mode for the process orchestrator and Autoscaling for the production scaling model.

Request journals and orchestration ownership

C# owns request generation, pacing and latency measurement. The unified driver and MemoryLab compile the same percentile interpolation from benchmarks/Common. Python controls process/pod faults and independently reconciles receipts. Shell scripts prepare environments and invoke these tools; they must not introduce another load generator or silently retry application requests.

Use --journal-directory <new-directory> with run or MemoryLab load when individual outcomes matter. Each process creates a unique JSONL file containing its pod UID, writer ID, UTC and monotonic clock, caller ID, target URI, length and SHA-256 when available, response headers/status/version and transport exceptions. Async response headers also retain QueueElementId, linking the caller ID to the accepted queue element before execution and acknowledgment reconciliation. Intents are flushed before entering the HTTP transport. An exception after that point is recorded as unknown; it is not proof of rejection or non-execution. MemoryLab sync/async calls share the caller ID and SHA-256 with the independent function fixture, and record operation completion only after response validation and draining. Sync still sends one application-level request; no retry is added.

JSONL lines are flushed to the OS, without a per-line disk fsync. They survive a process crash when the OS retains the file; they do not prove host power-loss durability. The independent Python function receipts retain their existing fsync. The HTTP pilot journal observes response headers, not successful full-body consumption. It does not observe transparent transport retries or redirects as separate wire exchanges. Reconcile those with server receipts and runtime logs. Journaling is opt-in and adds driver hashing/I/O cost; use the same setting and binary for both sides of a comparison. Original reports are never retrofilled.

The Kubernetes pod-replacement adapter reuses the three-node campaign manifests and executes the C# generator as a Job. It keeps the deleted function process alive during preStop to distinguish stale connection reuse from pod selection. Function headless DNS excludes unready addresses; Raft's separate headless service retains its own membership policy. API observations include pod UIDs/IPs, termination/readiness, EndpointSlices and events. Runtime debug logs retain the actual sent URLs; receipt headers identify the function that served each request.

The default --replacement-mode terminating retains those established connections until the observation window ends. Use --replacement-mode exit for a separate case where deletion also ends the old fixture process. Its identity is checked before SIGINT, and a replacement UID is never signaled by that action. Keep these two failure modes distinct in the report. --function-delay-seconds 0.5 optionally holds function requests in flight; combine it with C16 and a suitable target rate to exercise active connections rather than merely configuring 16 idle slots. The delay applies to POST workload calls, leaving readiness GETs unaffected. Use --function-controller statefulset --replacement-mode exit to exercise a StatefulSet function with a stable ordinal and a replaced UID/IP. The old process must exit before that controller can recreate its ordinal; the adapter rejects the long preStop mode for this case.

For a separate forensic run, --delivery-trace enables Trace logging at admission, dequeue, HTTP transport entry/result, callback command and committed Raft apply boundaries. Join caller journals' QueueElementId to queue element IDs, worker generation/try number, producer generation/sequence, operation request ID and Raft index/term. A transport entry does not prove bytes reached the function. A network exception may become the existing synthetic HTTP 500; the transport trace keeps that outcome distinct from actual response headers. A confirmed callback command is distinct from proof that it matched a still-running attempt. Missing trace lines never prove non-application; preserve WAL/snapshots for replay, especially on followers and restarts that have no local apply context. Trace logging adds I/O cost: keep this diagnostic separate from ordinary performance acceptance.

Routing cases also use the existing resource sampler to read the owned runtime's CPU ticks, RSS, open FDs and socket FDs every five seconds. Live TCP states are matched to that process's socket inodes; TIME_WAIT and interface byte counters belong to the entire pod network namespace, including probes and diagnostics. Keep this scope and sampler overhead identical across comparisons. Each sample includes pod UID and process start identity; a recycled PID is rejected. Sampling never signals a process and does not rehash the executables on every poll.

During routing teardown, the adapter first scales its owned workloads to zero. It then ends only its Python function fixture, checking namespace/campaign labels, image, command, downward-API pod UID and the container PID1 command before SIGINT. This happens after measurement, keeping the long preStop from adding ten minutes to every case. Other processes are never signaled, and the retained-volume/log quiescence check still runs before export.

For async or mixed routing, the C# generator stops admitting work before a separate 180-second read-only receipt drain. The sampler marks that interval as drain. There is no resubmission.
