How SlimFaas Works

In Kubernetes, SlimFaas identifies its listener container by the configured Raft TCP port when the pod contains multiple containers with declared ports. Its HTTP server opens only that container's TCP ports, excluding Raft itself. This keeps monitoring and control sidecars from colliding with SlimFaas at startup. A single-container pod retains its declared TCP ports. With multiple containers, missing or ambiguous Raft-port ownership fails closed with an explicit diagnostic.

Kubernetes function pods are associated with their exact controller identity. Deployment pods must reference a ReplicaSet whose controller name and UID match the Deployment; StatefulSet pods must reference that StatefulSet's current UID. This includes both ReplicaSets during a rollout and excludes orphaned or stale owners after a same-name recreation. Prefix matching is not used for routing.

Durable Streams persist definitions, subscriptions, message bodies, attempt leases, ACKs and retention gaps through the unified SlimData Raft batch path. HTTP dispatch is leader-owned; WebSocket-owning nodes reserve through the same shared state. SLDC/6 adds atomic file-admission commands to the WebSocket directory contract; stored producer receipts from earlier formats remain readable. SlimData payloads use generated MemoryPack readers and writers directly, without changing the wire format. Readers rent their own temporary state and avoid a partially published root formatter during concurrent startup/WAL replay. Unexpected runtime decoding or validation exceptions propagate; only known structural/serialization errors are classified as incompatible batch payloads. API payloads use source-generated JSON. Upgrade all Raft nodes together: mixed SLDC/5 and SLDC/6 clusters are deliberately not ready.

The file-admission state machine stores a pending pin before file publication. A successful commit publishes its physical-file descriptor and queue element, or public alias, with the active reference in one state snapshot. It checks the configured number of persisted-copy proofs and rejects shared node or declared volume identities. Retiring an admission checks current queue, DLQ/replay and public-alias ownership again inside Raft. An expired admission cannot be revived by a delayed commit. A persisted, nondecreasing leader clock also rejects its original delayed begin after the retired record has been collected. Physical IDs must be unique for each admission; public names are replaceable aliases. The state machine cannot independently attest storage hardware or copy persistence: proofs must come from the verified file-copy path. This internal path is used by the opt-in durable HTTP acceptance policy. Background repair walks active admissions and legacy references without retaining queue bodies or old state snapshots across transfers; see Files.

WebSocket registrations use a Raft-backed connection directory with node leases and incarnation fencing. Configuration reservations are cluster-wide; only activated, live-owner registrations appear as virtual replicas. Sync and async ingress relay directly to the owning node, while event fan-out groups targets by owner and preserves best effort. Stream reservations remain owner-local. Internal proofs bind sender membership, owner incarnation, operation and payload; credentials stay in private state, outside Data APIs and workload environments. The synchronous relay uses a dedicated duplex HTTP transport: response-duration metric wrappers cannot wrap upgraded WebSocket streams. Async and event relays keep the standard instrumented HTTP client. See client routing and failure semantics.

SlimFaas sits between callers and their applications. It routes HTTP requests, wakes idle workloads, queues asynchronous work, dispatches jobs and coordinates state through SlimData.

Routing and wake-up queries use explicit ZLinq value enumeration for function lookup and first-ready-pod port selection. Function lookup remains ordinal, case-sensitive and first-match, and reads the current deployment snapshot on each call. Arrays and lists avoid query iterator allocations; other collection implementations remain supported. Materializing pipelines also use value enumeration for job caller resolution, HTTP headers, status and virtual-replica projections, local topology, metrics/activity workers, stream dispatch and SlimData batches. DLQ staging still deep-clones mutable queue attempts while sharing immutable payload memory; its wire format is unchanged. Value queries stay within synchronous scopes, and task/DTO collections are materialized before awaiting. Deferred IEnumerable<T> APIs remain deferred. Predicated counts and readiness checks keep .NET 10 LINQ, whose array/list fast paths already avoid iterator allocations. There is no global LINQ replacement. Queue-state selections also use value queries so sparse running/retry/finished snapshots allocate storage for their matches instead of a builder sized to the whole queue. The filtered value query materializes an owned array and wraps it as immutable without another copy; this also avoids growing immutable builders for dense selections. The selected elements retain their original identities and payload ownership. Stream counters scan pending deliveries once without a temporary array; key/value batch projections, queue result projections, batch statistics and file-transfer peer selection also use explicit value enumeration. File-tag sorting and active Stream counts retain LINQ after comparative measurements. See performance measurements for local-cluster and allocation benchmarks.

Start with the Guided Tour to see these flows in the dashboard. This page explains what happens behind each step; the API Reference lists the actual routes.

Durable terminal failures

Opt-in Dead Letter Queues share SlimData's ordered Raft mutation pipeline. Terminal callbacks, dequeue-time exhaustion, and maintenance timeouts atomically replace an executable request with retained metadata/payload references. Replay atomically creates a fresh active element and a 24-hour receipt. Metadata is stored separately from serialized request bytes so retention, owner checks, and SSE summaries do not copy retained bodies. The existing artifact cleaner protects retained/replayed owners until their last reference is released. DLQ state stays outside executable queue counts.

Committed transition counters and a bounded recent-transition window are replicated with snapshots. Browser snapshots are projected per caller; private DLQ state never enters the shared public SSE frame cache. DLQ metric scraping uses the same dedicated access policy rather than the public metric registry.

Container build dependencies

Dockerfiles pin the .NET 11 SDK to 11.0.100 and .NET runtime images to 11.0.0. Alpine-based builds and runtimes share Alpine 3.24 (3.24.4 for standalone Alpine images). Frontend build stages use Node.js 26.13.1 LTS on Alpine 3.24, and the FibonacciReact demo serves its generated assets with stable nginx 1.30.6 on Alpine 3.24.

The SDK and runtime pins must be upgraded together. NuGet audit checks all direct and transitive dependencies, including the Native AOT compiler; vulnerability warnings fail the build.

The SlimFaas and MCP dashboards install dependencies with npm ci; the React demo uses pnpm with a frozen lockfile. Updating a dependency therefore requires its corresponding lockfile to be committed. Generated frontend assets and local test/demo artifacts are excluded from the Docker context. The MCP final image explicitly copies the freshly built dashboard into wwwroot, including on the first publish from a clean checkout. All .NET container builds use the repository root as their build context so central package versions, analyzers and AOT checks apply consistently:

docker build -f Dockerfile -t slimfaas:local .
docker build -f src/SlimFaasMcp/Dockerfile -t slimfaas-mcp:local .
docker build -f samples/FibonacciReact/Dockerfile -t fibonacci-react:local samples/FibonacciReact

See the dependency update guidelines for compatibility constraints, license checks and validation commands.

Dependency compatibility holds

Frontend tooling uses Node 26 LTS and pnpm 12.21.0. pnpm configuration, including transitive overrides and explicitly allowed build scripts, lives in each package's pnpm-workspace.yaml.

Mermaid remains pinned to 11.17.2: Mermaid 12 introduces EPL-2.0 elkjs, which is outside the CNCF license allowlist.

ESLint and @eslint/js remain at 9.39.5 because the current React plugins do not support ESLint 10. The documentation site keeps TypeScript 6.0.3 because typescript-eslint cannot use the TypeScript 7 API; the Vite dashboards use TypeScript 7. Storybook's docgen plugin uses patched glob 14.0.4 or later through a scoped override. These constraints can be revisited when upstream supports the newer tooling.

The Python client retains Python 3.10 support with websockets 16.x. Pygments 2.19.2 is held until a newer distribution passes FOSSA. The existing OpenTelemetry Prometheus exporter remains at 1.20.1-beta.1 because there is no stable release of that package.

ASP.NET Core 11.0.0 trimming workaround

SDK 11.0.100's Microsoft.AspNetCore.Components.Endpoints assembly embeds an ILLink.Substitutions.xml resource naming Microsoft.AspNetCore.Components.Forms instead of its own assembly. Managed trimmed SlimFaas publishes therefore fail with IL2101. A linker attribute file scopes an exception to IL2101 on that exact framework assembly for this SDK. Its Blazor Hot Reload substitution is unused by the React host. Application trimming/AOT analysis and warnings-as-errors remain enabled. Remove the workaround when the framework resource is corrected.

Native build toolchain

Source builds require .NET SDK 11.0.100 or a newer .NET 11 SDK, as selected by global.json. This selects the Native AOT compiler and runtime 11.0.0, including the Brotli security fix. It also retains the compiler fix shipped in .NET 10.0.12 for Apple's linker assertion, too many large addends, which can affect SlimFaas's generated Kubernetes client code on macOS. Upgrade the SDK before publishing a native macOS build. The setting also applies to the standalone bundle's sample executables and does not affect other RIDs. The fix is documented in the upstream .NET runtime backport.

Components and responsibilities

Each SlimFaas node serves requests and observes the cluster. ReplicasSynchronizationWorker refreshes workload topology. The leader's scaling and dispatch decisions use readiness, dependencies, activity history, concurrency limits and queue state.

SlimWorker dispatches queued HTTP work. WebSocket workers deliver requests to registered clients. Job workers create executions through the orchestrator, while schedule workers enqueue due jobs. HistorySynchronizationWorker shares recent activity history used by scaling.

SlimData holds replicated queue state, configuration and small values. ClusterMembershipAnnounceWorker announces a member to a leader; SlimDataMembershipReconciliationWorker reconciles membership with the orchestrator topology. Node readiness includes Raft recovery and protocol compatibility.

Raft HTTP sockets release unsent data when a connection closes. This prevents cancelled large uploads to a silent peer from retaining TCP buffers across retries; it does not change the request/election deadlines or persisted Raft format. Successful connections remain pooled. The .NET socket linger contract explains the difference between waiting to transmit queued data and discarding it during socket closure. Linux cgroup socket memory is measured separately from process RSS in the reliability controls.

Membership reconciliation uses one topology snapshot per cycle. A removal requires a positive requested replica count, exactly that many distinct eligible endpoints, and the local endpoint in the snapshot. Eligible pods have started and have an IP; they do not need to be ready. A replacement pod that is absent, pending or waiting for an IP therefore does not cause the remaining members to shrink the Raft quorum. Eligible new members can still be added while the topology is incomplete.

A real scale-down retains the existing SlimData:Membership:RemovalMissingCycles confirmation threshold (three by default). Removal observations reset when the topology is incomplete, the local endpoint is missing, an addition is attempted, or leadership, consensus or the leader lease is unavailable. A complete topology must then be observed for the full threshold again. Debug logs report the requested replica count and eligible endpoint count when removals are deferred. This guard does not automatically repair an already divergent membership configuration or restart a stalled process; see data-preserving Raft recovery.

Event-driven Kubernetes synchronization (watch-as-signal)

On Kubernetes, the synchronization workers are driven by watch streams instead of fixed-cadence polling: watch events on pods, deployments, statefulsets, jobs and cronjobs only signal that something changed, and the existing LIST-based synchronization then runs unchanged — the synchronized state is identical to polling, just triggered by events, with a periodic resync as a safety net (see the configuration reference in Get started on Kubernetes).

How the watch is Native AOT compatible. SlimFaas references KubernetesClient.Aot, the trimming/AOT variant of the official client. That package replaces the reflection-based deserialization of LIST/GET calls with source-generated System.Text.Json contexts, but it does not ship Watcher<T>/WatchAsync: the standard client's watch machinery deserializes every event into typed models (V1Pod, V1Deployment, ...) through reflection, which is incompatible with trimming and Native AOT. SlimFaas works around this by never needing that machinery:

  • Transport — raw HTTP, only the client's plumbing. KubernetesWatcherWorker builds its own HttpRequestMessage (GET {BaseUri}.../pods?watch=true&allowWatchBookmarks=true...) and borrows only three pieces of the client, none of which serialize anything: client.BaseUri (API server URL), client.Credentials.ProcessHttpRequestAsync (ServiceAccount Bearer token with its rotation, or mTLS) and client.HttpClient (the configured TLS pipeline). This is the same hand-rolled pattern ScaleAsync already used, so the path was AOT-proven before the watcher existed. The response is read with ResponseHeadersRead and StreamReader.ReadLineAsync — a Kubernetes watch stream is line-delimited JSON.
  • Parsing — three scalar fields, zero reflection. The watch-as-signal design never materializes the Kubernetes object carried by an event. WatchEventLineParser extracts only the event type (ADDED/MODIFIED/DELETED pulse a version counter, BOOKMARK, ERROR), object.metadata.resourceVersion (stream continuity across the 60 s server-side rotations) and object.code (410 Gone detection inside ERROR events). It uses Utf8JsonReader — a forward-only BCL ref struct with no reflection and no dynamic code generation, AOT/trim-safe by construction — with UTF-8 literal property comparisons (ValueTextEquals("type"u8)); everything else in the line (the full spec/status) is skipped without ever being interpreted, and a malformed line yields Unknown instead of throwing.
  • State — the typed path stays on the supported client. The actual cluster state is still obtained by the existing LIST calls (ListNamespacedPodAsync, ...), which go through the AOT client's typed APIs and their source-generated serialization. The type-rich work therefore remains entirely on the path KubernetesClient.Aot already supports; the watch only decides when those LISTs run.

This split is validated by the CI, which publishes Native AOT builds for linux x64/arm64, win-x64 and osx x64/arm64 — reflective code on the watch path would be broken or flagged by the trimmer.

Synchronous calls

sequenceDiagram participant C as Caller participant S as SlimFaas participant O as Orchestrator participant F as Function C->>S: /function/name/path S->>S: Resolve function and check access opt Function has no ready replica S->>O: Request wake-up with dependencies O-->>S: Replica becomes ready end S->>F: Forward HTTP request F-->>S: Application response S-->>C: Stream status, headers and body

A synchronous call waits for a usable replica and the application's response, subject to configured timeouts. Visibility failures are represented as 404. A wake endpoint only requests activity and returns 204; it is not a readiness wait. Streaming responses do not require buffering the whole response in memory.

Asynchronous calls and callbacks

sequenceDiagram participant C as Caller participant S as SlimFaas participant D as SlimData Raft participant W as Dispatch worker participant F as Function C->>S: /async-function/name/path S->>D: Durably enqueue request D-->>S: Committed S-->>C: 202 Accepted D-->>W: Work available W->>F: Dispatch when ready and within concurrency limit alt Function completes in its HTTP response F-->>W: Completion status W->>D: Commit queue outcome else Function accepts deferred completion F-->>W: 202 Accepted F->>S: /async-function-callback/name/id/success S->>D: Commit callback outcome end

202 acknowledges durable enqueueing, not execution or a stored function result. Handlers can be retried after failure or incomplete delivery; make side effects idempotent. Retry delays, HTTP timeouts and retryable statuses are configured per function. Terminal failures can be atomically retained in an opt-in DLQ and replayed as a fresh queue execution after repair. See Async Functions.

Committed mutations signal workers immediately; periodic polling remains a recovery fallback. Dispatch uses a lightweight queue snapshot of counts, running IDs and reservations rather than copying every payload. Completion mailboxes group durable callbacks, release response resources promptly and perform offloaded-body cleanup separately. Results completed after leadership loss are discarded locally so the current leader controls callback and retry decisions.

An expired Raft reservation does not release a request that the current HTTP worker still owns. If its snapshot no longer lists such a request as running, the worker drains completed responses again and defers another dequeue for that function until ownership is resolved. This prevents free slots from reserving the same ID while its HTTP request or durable callback is still pending. It does not consume an extra retry, alter the configured timeout or change Raft commands.

For inline HTTP bodies of at least 64 KiB, dispatch reads the body through a read-only stream over its owned queue packet. Preparing a batch no longer clones each large body before sending any request. The stream remains owned until the HTTP attempt completes or is canceled. Small bodies and file references retain their existing paths; the persisted request format and file-offload threshold are unchanged.

Events

sequenceDiagram participant C as Publisher participant S as SlimFaas participant A as Ready subscriber replica A participant B as Ready subscriber replica B C->>S: /publish-event/event/path S->>S: Resolve allowed subscriptions par Ready replica A S->>A: Forward method, path and payload A-->>S: Application response and Ready replica B S->>B: Forward method, path and payload B-->>S: Application response end S-->>C: 204 No Content

HTTP events fan out to ready replicas, including multiple replicas of the same function. They do not durably queue for sleeping functions or wake them. The handler logs per-target failures; 204 does not guarantee every subscriber succeeded. With no allowed configured subscriber, it returns 404. Connected WebSocket subscribers receive events through their transport. See Events.

Durable Streams

flowchart LR Publisher -->|Append| API[SlimFaas API] API -->|Commit| Log[(Retained SlimData Raft Stream)] API -->|202 with message ID after commit| Publisher Log -->|Independent subscription| A[HTTP function A] Log -->|Independent subscription| B[WebSocket function B] A -->|ACK or callback| PA[(A progress)] B -->|ACK or callback| PB[(B progress)] PA --> Log PB --> Log

Publishers do not wait for consumers. One function's disconnected client, callback wait or retry does not gate another function's progress. Each function shares consumption state across its replicas; a message goes to one replica per attempt, not every replica. HTTP delivery is leader-owned and WebSocket delivery is owner-local, with reservations and ACKs persisted through Raft.

ACK advances consumption without deleting history. Retention remains bounded by age and count, so idempotent consumers must account for possible retention gaps. Terminal Stream failures remain in Stream progress and are not automatically copied into async-function DLQs. See the Stream architecture and sequence.

Jobs and schedules

A job configuration describes the executable/image, arguments, environment, resources, dependencies, concurrency and retention. A request adds an execution and returns its ID. Dynamic schedules create executions when due; Kubernetes CronJobs can also provide annotated job configuration. Deleting a schedule stops future submissions, while deleting an execution targets that individual job. See Jobs.

Scaling and access

Inactivity can reduce replicas to the configured minimum, including zero. New calls and wake-up requests refresh activity. Dependency checks coordinate dependent workloads. PromQL triggers handle scale-out from running replicas, with limits, stabilization windows and policies. Read Autoscaling before tuning these independently of request timeouts.

Function visibility, path overrides and event subscription visibility are separate decisions. DefaultFunctionAccessPolicy classifies a caller by the address of its TCP connection, compared exactly with the Trusted function pod and job pod addresses; the peer endpoints apply the same rule with the SlimFaas member addresses. X-Forwarded-For is ignored unless SlimFaas:TrustedProxies lists the proxies allowed to set it, in which case the forwarded-headers middleware rewrites the connection address (one hop) before any classification runs. See Functions. Native local mode's shared loopback network cannot demonstrate pod isolation. Data sets/files have their own visibility setting; the API Reference documents the current hashset behavior separately.

Queue metrics and function isolation

The autoscaler evaluates application metrics within the function's own deployment. SlimFaas emits the three built-in queue gauges from its own metrics endpoint, so those series are additionally selected from the slimfaas source when their function label matches the function being scaled. Other functions' queue values and unrelated SlimFaas metrics remain excluded from scoped evaluations.

The guided scale-out exercise uses that queue signal to show one ready replica becoming several, followed by queue drain and scale-down.

Data storage and replication

flowchart LR Client[Client] --> API[Data API] API -->|Small values and metadata| Raft[(SlimData replicated state)] Raft --> PeerState[(Peer state)] API -->|File stream| Disk[(Receiving node disk)] Disk -.->|Announce availability| Peer[Peer node] Peer -->|Pull content when needed| Disk Peer --> PeerDisk[(Peer disk cache)]

Small sets, counters and queue mutations are applied through SlimData's replicated log. Counter operations execute atomically as commands. The HTTP hashset facade stores one raw value field.

Each node batches outgoing SlimData mutations in a local command consumer (one per configured partition). Dequeueing an asynchronous request is itself a durable mutation: a stalled local consumer can therefore stop dispatch even when functions are Ready and Raft continues committing writes from other nodes. Check local batch queue growth and dispatch-cycle progress together with Raft health.

An outgoing mutation request uses both the current local Raft consensus token and an observed-leader generation for its lifetime, including the HTTP response body. The leader-change event also retires the generation: a follower can observe a new leader without its captured consensus token being cancelled. When either epoch ends, the old request is cancelled and the ordered consumer retries the same producer/generation/sequence against the newly observed leader. This avoids holding every later command until the old HTTP request's 100-second default timeout. A previously committed attempt is resolved through the existing batch deduplication; no request is skipped to unblock the queue. The configured HTTP timeout still bounds a request within a valid epoch.

Each producer retains its last response for this deduplication. Reading its next sequence borrows the persisted response bytes instead of copying a potentially large dequeue reply. Responses of at least 64 KiB are serialized directly into their final session buffer, avoiding another large pooled intermediate. The generated MemoryPack format, cached response contents and sequence checks remain unchanged, so existing producer receipts can still be replayed after an upgrade. These allocation reductions do not remove the need to size memory for queued payloads and concurrent deliveries.

Large dequeue replies also avoid a response-sized pooled serialization buffer. The generated formatter first measures its output with reusable scratch storage, then writes the same bytes into the final array. Small replies keep the existing serialization path. A formatter's oversized final reservation is staged in a scratch tail so UTF-8 strings do not add padding or change the wire format.

The batch HTTP client reads a known Content-Length directly into one response array. The configured HTTP timeout remains active through the response body, together with leader and consensus cancellation. Older or chunked peers retain bounded buffering; changing to headers-only completion does not permit an unbounded body wait.

The consumer stops after 15 seconds of inactivity and starts again when a command arrives. Admission, retirement and disposal are synchronized so that a command arriving during retirement remains owned by exactly one consumer. An unexpected consumer exception is logged and explicitly fails its unfinished operations; the next enqueue can start a new consumer. The batcher does not automatically replay failed operations, because an interrupted write may already have committed. This recovery does not change Raft messages, persisted data or function retry configuration. Upgrading to a release containing this fix prevents the negative idle-timeout failure; on older versions, restarting the affected SlimFaas pod is a temporary workaround, not a repair of the underlying race.

File content is disk-backed; metadata is cluster-consistent. A receiving node announces availability and another node can pull content when serving a download. File bytes are not copied through Raft as ordinary large values. TTL and deletion govern temporary artifact availability. See Data Sets and Data Files.

Consensus and persistence

Protocol probes have a two-second deadline covering connection, response headers and body. A silent or suspended member is classified as unavailable, so a newly elected leader can still check the remaining reachable members. Caller shutdown cancellation propagates. An explicit incompatible protocol still blocks writes, and ignoring an unreachable probe never replaces Raft's quorum/lease checks. This prevents an unbounded protocol HTTP read from holding a healthy majority unavailable after a leader change; request and async-drain deadlines are unchanged.

SlimData uses Raft through DotNext. Nodes retain applied state in memory and persist commands in a write-ahead log. A healthy quorum is needed for replicated writes; local snapshots of status and metadata do not by themselves establish that every peer is caught up.

SlimData uses DotNext 6.12.0. This retains upstream fixes for a full replication queue silently losing a member response and for rejecting an election candidate whose log is shorter but whose last term is newer. These are stabilization fixes; they do not establish the cause of a particular operational incident. The SlimData command protocol, snapshot payload format and AppendEntries commit-index guard are preserved.

SlimData's WAL adapter waits for the append's flush/recovery checkpoint before returning to the Raft transport. DotNext's buffered append can otherwise return before its background flusher persists the newly received tail. Under disk exhaustion and process failure, that volatile acknowledgment can leave a quorum without a previously accepted entry. The adapter keeps the same WAL layout and memory strategy, propagates flush failure/cancellation, and allows the existing flusher to coalesce concurrent writes. Flush-completion observation is serialized because the underlying completion source supports one waiter. Commit and explicit flush calls share the same observer gate, including calls through Raft interfaces; appends remain concurrent. See the versioned append implementation and flush/checkpoint implementation.

Read paths additionally wait for the local state machine to apply the visible commit after the leader barrier. This covers DotNext's weak-leader fast path, which may return before that local application. The existing read timeout still bounds the complete operation.

Version 6.12.0 also corrects an empty-heartbeat response that could delay leader lease renewal after a write burst when one voter stops responding despite a healthy majority. The fix applies to the HTTP transport; see upstream issue 309 and its fix. The Local lease-burst campaign records actual write latency while a follower is suspended. This upstream defect has not been established as the cause of all recorded Windows publication or recovery failures. Existing WAL chunk geometry and SlimData payload formats are unchanged; do not reset state or assume rollback safety from a forward replay.

The upgrade must preserve live member re-addition, legacy WAL metadata pages on hosts with system pages larger than 4 KiB, and compatibility with legacy Raft HTTP headers. See the validation record before upgrading existing state. Do not infer safe rollback from a forward-upgrade test.

SlimData recovery

SlimData implements DotNext's public IStateMachine and ISnapshotManager contracts for its snapshot lifecycle; Raft consensus and the WAL remain DotNext. Incoming snapshots are written to a temporary file in the same directory, checked against their declared length, flushed to disk and decoded into detached state. Only successful completion publishes the index/term filename and replaces the in-memory payload. Cancellation, short input and I/O errors retain the previous state and cannot promote an incomplete temporary copy. Snapshot transport and serialization use bounded 64 KiB I/O buffers, independently of WAL chunk geometry.

Older receivers could leave truncated files under final snapshot names. Startup logs and retains those files when decoding reaches unexpected end-of-file, then tries an older complete snapshot before WAL replay or peer synchronization. If none is complete, startup fails explicitly instead of accepting an empty reset. Unexpected decoding failures still propagate. The snapshot payload and filenames remain compatible with historical formats; the 6.6.0 WAL/snapshot fixture is part of the regressions. Snapshot lifecycle code adapted from DotNext carries its MIT notice in src/SlimData/ThirdPartyNotices/DotNext.txt and published output.

DotNext 6.12.0 chooses the synchronization path internally. SlimFaas supplies warmupRounds (100 by default): a restarted member first attempts WAL backtracking and can fall back to DotNext snapshot recovery when the gap is larger than the configured search window. There is no public API in this version to force a snapshot for a particular follower.

The SlimData diagnostics metrics expose the locally measurable recovery state: slimdata_raft_local_apply_lag (local WAL entries pending application, not leader/follower replication lag), slimdata_raft_wal_generation_rate, slimdata_raft_catch_up_rate, slimdata_raft_catch_up_cannot_converge, slimdata_raft_recovery_mode{mode="wal|restoring|unknown"}, and slimdata_raft_recovery_duration_seconds. The convergence gauge is an early-warning signal, not a membership failure: it is set when the observed local apply rate is below the observed WAL generation rate. If an alternate audit-trail implementation does not expose an applied index, lag and recovery metrics remain zero because that state cannot be measured safely.

slimdata_raft_progress_stalled becomes 1 when the local WAL has entries pending application and the applied index has not changed for 30 seconds. It is sampled every five seconds using monotonic time, logs only transitions, and clears on progress or when the backlog disappears. Idle nodes without a backlog remain at 0. This informational signal does not change readiness, membership or restart behavior. See Raft incident collection.

A cluster can also lose its leader while every local entry is already applied. slimdata_raft_has_leader and slimdata_raft_consensus_unavailable_duration_seconds cover this independent failure mode. The duration accumulates while the leader is absent or consensus is unavailable and resets only when both return. The five-second sampler logs availability transitions and a reminder every 60 seconds. Identical readiness warnings are shared across waiters and limited to once per 60 seconds; a new reason or a new outage is reported immediately. None of these diagnostics restarts a node or changes its persisted state.

SlimData WAL and snapshots

Both the SlimFaas host and standalone SlimData restore the latest snapshot before resolving Raft services or starting hosted services. DotNext 6.11.1 requires this ordering before constructing the write-ahead log when a snapshot exists. Empty databases follow the same startup sequence. Restoration failures stop startup; WAL application must not race snapshot loading. DotNext 6.11.1 also rejects WAL construction if restoration was omitted, including through the dependency-injection registrations. A regression test exercises this guard with a compacted legacy WAL; new hosts must preserve the startup sequence.

DotNext 6.11.1 writes a checkpoint on every WAL commit to preserve consistency. Its former FlushInterval and FlushOnCommit settings are deprecated and have no effect; SlimFaas does not set either option. This upstream durability change applies to both memory-management strategies and can affect write throughput. See the upstream release notes.

DotNext supports two WAL memory-management strategies. SlimFaas selects the strategy with SlimData:WalMemoryManagement:

  • SharedMemory is the default. It writes directly to memory-mapped WAL files so the operating system can reclaim or flush mapped pages under memory pressure.
  • PrivateMemory uses private temporary buffers and asynchronous write-through I/O. It can improve write throughput but consume more RAM, especially when opening a large existing WAL.

WAL directories created by SlimData on Windows use 64 KiB data chunks. Smaller system-page chunks can require hundreds of synchronous mapped-file flushes per large Raft entry, causing repeated RPC cancellation before a healthy majority can acknowledge it. The chunk size is persisted in wal/slimdata-chunk-size before the first page is created and read before opening the WAL, including on other operating systems. Existing unmarked WALs keep their historical system-page geometry. New Linux and macOS WALs use the host page size, which is 16 KiB on the ARM64 Mac used in the benchmark campaigns. The macOS comparison with 64 KiB exceeded the non-regression limits in both the initial campaign and repeat. Keep the geometry used at creation when reopening an existing WAL. Preserve the marker in backups and use a reader that supports it.

Windows strategy controls show faster large publications with explicit PrivateMemory, but later recovery checks still failed. A trial Windows default change was therefore withdrawn; see the recorded controls and remaining reliability gates.

SlimData creates a streaming snapshot when either 32 MiB of successfully applied WAL entries or 500 successfully applied entries have accumulated, whichever occurs first. A snapshot compacts the preceding Raft log window; the byte and entry counters restart after the snapshot request or a snapshot restore.

{
  "SlimData": {
    "WalMemoryManagement": "SharedMemory",
    "SnapshotIntervalEntries": 500,
    "SnapshotIntervalBytes": 33554432
  }
}

The equivalent environment variables are:

SlimData__WalMemoryManagement=SharedMemory
SlimData__SnapshotIntervalEntries=500
SlimData__SnapshotIntervalBytes=33554432

WalMemoryManagement accepts only PrivateMemory and SharedMemory, case-insensitively. Snapshot intervals must be strictly positive. Invalid values stop startup with a configuration error. Changing the memory strategy does not change the WAL format and does not require a data migration.

A failed background WAL flush or application leaves the current DotNext WAL instance terminal, even after disk space returns. The diagnostics worker checks that state through a bounded, read-only application barrier and stops the host on WriteAheadLog.InternalException. Configure a supervisor or Kubernetes restart policy and retain the original volumes. Atomic index gauges alone do not detect this failure. Ordinary catch-up delays remain observable and do not stop the host. On Linux, exhausting the filesystem backing SharedMemory can also terminate a memory-mapped writer immediately; the restart must still use the retained WAL and snapshots.

The current byte window and the cause of the latest snapshot request are exposed as slimdata_wal_bytes_since_snapshot and slimdata_snapshot_last_trigger{cause="bytes|entries|incompatible"}.

Snapshot layout and reserved pod IPs

When the dispatch worker dequeues an asynchronous request, it reserves a pod IP for it within the per-pod concurrency limit (NumberParallelRequestPerPod) and SlimData stores that IP on the queue try. On every dispatch cycle the worker reads the running tries and their reserved IPs from the queue state and keeps those pod slots occupied before reserving pods for the next messages.

SlimData snapshots persist the reserved IP of every queue try so that this accounting survives a snapshot restore (node restart, follower catch-up, snapshot installed by the leader). The snapshot body keeps the historical layout unchanged; the reserved IPs travel in a trailer written after the body. A node running a release without the trailer reads the body and ignores what follows.

Compatibility rules between releases:

  • Rolling upgrade: a snapshot written by the current release restores on an older node with empty reserved IPs. Nothing else is lost.
  • Older snapshot: a snapshot written by a release without the trailer (0.84.4 and earlier) restores on the current release with empty reserved IPs. Requests that were running when the snapshot was taken no longer count against their pod until they complete, time out or are retried, so a pod may temporarily receive more concurrent requests than its limit.
  • Downgrade: an older release drops the reserved IPs on its first restore, with the same transient effect. The body is unchanged in both directions, so no data migration is needed.
  • Corruption: a trailer that is truncated, carries an unknown magic or version, describes a different number of tries than the body, or is followed by extra data is rejected and the restore fails. A truncated new-format snapshot is never read as an older one, so reserved IPs are never dropped silently.

CPU-aware rate limiting

SlimFaas includes built-in load shedding, enabled by default, to protect your cluster during traffic spikes by automatically rejecting requests when CPU usage reaches configurable thresholds.

Key Features

  • Hysteresis support: Prevents rapid toggling between limited and normal states with separate high/low thresholds.
  • Port-specific: Applies to all SlimFaas ports except the SlimData internal port (used for cluster coordination).
  • Path exclusions: Configurable list of paths to exclude (e.g., health checks, metrics endpoints).
  • Native AOT compatible: Minimal performance overhead.

How It Works

  1. Monitoring: A background service continuously samples process CPU usage at a configurable interval, normalized by the number of processors available to the .NET runtime.
  2. Activation: A sample at or above CpuHighThreshold (80% by default) activates rejection of non-exempt requests with 429 Too Many Requests.
  3. Deactivation: A sample at or below CpuLowThreshold (60% by default) clears the limitation. Samples between the thresholds preserve the previous state.
  4. Exemptions: The SlimData port (used for internal cluster communication) is always exempt from rate limiting.

Both transitions happen during CPU sampling, even when no requests arrive or only health probes are called. For example, samples of 85%, 50%, then 70% leave requests allowed after the 50% sample without restarting the pod. Previously, the middleware evaluated transitions only on non-exempt requests and could miss that recovery between calls.

Configuration

Add the following to your appsettings.json:

{
  "SlimFaas": {
    "RateLimiting": {
      "Enabled": true,
      "CpuHighThreshold": 80.0,
      "CpuLowThreshold": 60.0,
      "SampleIntervalMs": 1000,
      "RetryAfterSeconds": 5,
      "ExcludedPaths": [
        "/health",
        "/ready",
        "/metrics",
        "/SlimData"
      ]
    }
  }
}

Parameters:

  • Enabled (bool): Enable or disable CPU rate limiting.
  • CpuHighThreshold (double, 0-100): CPU percentage that triggers rate limiting.
  • CpuLowThreshold (double, 0-100): CPU percentage that stops rate limiting (must be < CpuHighThreshold).
  • SampleIntervalMs (int, ≥100): How often to sample CPU usage (milliseconds).
  • RetryAfterSeconds (int?, optional): Value for the Retry-After header in 429 responses.
  • ExcludedPaths (string[]): List of paths that bypass rate limiting (e.g., health checks).

Validation:

  • CpuLowThreshold < CpuHighThreshold
  • Both thresholds must be between 0 and 100
  • SampleIntervalMs must be ≥ 100

Port Exemption

The CPU rate limiting middleware automatically exempts the SlimData port (configured via publicEndPoint in your SlimData configuration). This ensures that:

  • Internal cluster coordination is never throttled
  • Raft consensus and state synchronization continue uninterrupted
  • Only external/public traffic on other ports is subject to rate limiting

This design keeps your control plane healthy even under extreme load.

Diagnose healthy probes with blocked function calls

/health, /ready, /metrics and /SlimData (including its subroutes) are excluded by default. A pod can therefore return 200 on its probes while rejecting /function/... and /status-functions with 429 and Retry-After: 5. A browser's error handling or wake-up overlay can make this appear to be a stalled application. An HTTP timeout without a response is a different symptom and does not, by itself, identify CPU limiting as the cause.

When monitoring is enabled, each pod exposes two gauges on /metrics after the first CPU sample, without additional labels:

Metric Meaning
slimfaas_cpu_usage_percent Latest CPU percentage used by the limiter.
slimfaas_cpu_rate_limiting_active 1 while limiting, otherwise 0.

SlimFaas.RateLimiting.CpuMonitoringWorker logs CPU rate limiting activated at Warning level and CPU rate limiting deactivated at Information level once per transition. High CPU usage detected remains a Warning for each sample at or above the high threshold. These gauges are absent when CPU monitoring is disabled.

Before restarting a pod, capture the failing request's status, response body and timing in the browser's Network panel and directly against each SlimFaas pod. For example, set your namespace and forward the first pod's public HTTP port (5000 by default):

SLIMFAAS_NAMESPACE=default
kubectl -n "$SLIMFAAS_NAMESPACE" port-forward pod/slimfaas-0 15000:5000

In another terminal, set a read-only function path for your environment:

SLIMFAAS_FUNCTION_PATH=/function/fibonacci1/hello/local
for path in /health /ready /status-functions "$SLIMFAAS_FUNCTION_PATH"; do
  curl --include --max-time 10 --write-out '\nHTTP %{http_code} in %{time_total}s\n' \
    "http://127.0.0.1:15000$path"
done
curl --silent --max-time 10 http://127.0.0.1:15000/metrics | rg '^slimfaas_cpu_'

Repeat for the other pods and retain their logs, including the interval before the failure. Compare direct responses with those through the ingress. If requests expire without 429, investigate routing, downstream connections and deployment synchronization rather than assuming the limiter caused the incident.

For a controlled development comparison, set SlimFaas__RateLimiting__Enabled=false in the SlimFaas deployment configuration and replay the same workload for a comparable duration. This temporarily removes CPU load shedding. A successful request immediately after the rollout is insufficient evidence: restarting alone also resets process state. Restore the setting after the comparison; the normal recovery path requires no restart.

Observe the system

The dashboard consumes /status-functions-stream: periodic state snapshots and live activity/activity_batch events. Animations are not a replay or an audit log. Peer nodes synchronize recent activity through an internal endpoint. See User Interface for sampling, batching and stream limits.

SlimFaas is compiled to native code with .NET AOT. Source-generated JSON and MemoryPack contracts keep serialization compatible with trimming. For reproducible measurements use Benchmarks; for traces and exports use OpenTelemetry. Advanced development references cover local cluster experiments and memory workloads.

Dashboard metadata projection

The optional /status-data-stream endpoint builds a metadata-only projection from locally applied SlimData state. A per-node lazy cache shares that projection across viewers at the existing state interval; no scan runs without requests. File lengths come from stored MemoryPack metadata, with no document reads or cluster file pulls. Only a bounded page is serialized to each viewer using the generated JSON context. Status and metadata streams share MaxSseClients. The data visibility policy applies unless SlimFaas:ExposeDataMetadata explicitly enables metadata access while the front is enabled. See the dashboard contract.

On-demand instance log readers

The optional SlimFaas:ExposeLogs capability exposes managed function, job and SlimFaas-node output through /status-log-sources and /status-logs-stream. It requires the front to be enabled and defaults to false. A source reference contains resource identity rather than a network address or log path; each open revalidates managed ownership and instance generation. Kubernetes validates controller ownership, Docker resolves a known container, and native nodes use the supervisor's existing authenticated control channel.

Per-node readers are shared only while viewed (four sources maximum) and use bounded line/byte buffers independent of client speed. The last disconnect cancels the upstream read. They reserve the same SSE client quota as Traffic/Data while leaving peer activity synchronization inactive. Native file tails, Docker stdout/stderr demultiplexing and Kubernetes follow requests use bounded streaming parsers, with generated JSON contracts for AOT. No SlimData payload or storage migration is required. See instance logs.

Autoscaling signal providers

Autoscaling obtains observations through the internal IScalerProvider contract. PrometheusScalerProvider owns PromQL compilation/evaluation and source-health checks; it reuses the existing scraper, compiled evaluator and metrics store. Providers return a state, numeric value and activity flag and have no Kubernetes replica-writing dependency. AutoScaler owns threshold formulas, aggregation and stabilization/policies; ReplicasService combines this with HTTP activity, schedules and dependency readiness. Providers are registered explicitly through DI, compatible with native AOT.

External series use reserved internal identities containing namespace, function, source and a URL fingerprint, within the existing MemoryPack snapshot shape. Historical local identities and queue-gauge scope are unchanged. External evaluation filters series before PromQL runs and requires selected series to be present in the latest successful scrape. Health is process-local and is reset on leadership changes; persisted samples alone cannot activate an external signal. Only the leader collects, using the existing bounded HTTP worker.

See external sources and migration.

Scaling diagnostics and simulation

MetricsScalingCalculator calculates trigger recommendations, bounds, policies and stabilization from explicit observations and read-only histories. ScalingDecisionCalculator combines that result with the captured HTTP/schedule, dependency and infrastructure context. AutoScaler and ReplicasService retain the production history/telemetry writes and orchestrator calls. Real cycles publish diagnostic decisions before application and record accepted or failed requests afterward.

The dashboard reads a separate bounded in-memory diagnostic journal. The journal has no role in making scaling decisions and is reset across leadership changes. Simulations use request-local metric and health copies plus copied autoscaler histories; compilation caches for edited queries are also request-local. They share the calculators without invoking production writes or the side effects of the existing PromQL debug endpoint.

Followers resolve the leader from configured Raft membership and reuse the configured application-port resolution for HTTP relays. State frames are briefly cached per function and leader, with a maximum of eight cache entries per node. Internal endpoints require the front, allowed ports and a direct connection from a recognized SlimFaas member IP; browser-supplied upstream addresses are not accepted. See the UI guide.

Multi-platform runtime image compilation

The root Dockerfile builds its static dashboard on BUILDPLATFORM. Its managed linux-musl-arm64 publication also uses the build host SDK, avoiding an emulated Roslyn/trimmer process; the requested RID still selects ARM64 runtime assets. The linux-musl-x64 Native AOT publication keeps an x64 SDK and linker, including when the Docker build host is ARM64. Final base images continue to use TARGETPLATFORM. See Microsoft's multi-platform container guidance.
